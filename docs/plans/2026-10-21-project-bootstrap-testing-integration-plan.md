## Целевой результат для нового проекта

### Сначала спецификация, затем архитектура и дерево

До выбора профиля агент читает принятую спецификацию, существующий код и решения проекта. Уже отвеченные вопросы не задаются повторно. Для отсутствующих решений выясняет только существенные требования:

| Независимое решение | Что нужно установить | Что нельзя выводить автоматически |
| --- | --- | --- |
| Frontend | Нужен ли UI, какой стек, отдельное приложение или часть fullstack-фреймворка | React не определяет серверный стек |
| Backend | Нужны ли собственные API/бизнес-правила, серверные функции, готовый backend-сервис либо их сочетание | Выбор облачной базы не отменяет собственный backend |
| Данные | Нужна ли БД, какая СУБД, схема, доступ, хранение файлов, владение миграциями | PostgreSQL не означает Supabase; backend может работать и без БД |
| Размещение | Где выполняется frontend и backend, где находится база; что уже существует | Провайдер базы не выбирает хостинг приложения и способ авторизации |
| Безопасность и тесты | Где проверяются права, какие роли и интеграции существуют, где безопасно тестировать | Нельзя заменять проверки API-полномочий проверками RLS или требовать RLS у каждого проекта |

Выбор записывается в существующий канонический контекст и `docs/architecture.md`: основание в спецификации, решение, затронутые пути, владелец и незакрытые вопросы. Отдельно фиксируются СУБД и её размещение. Неопределённый провайдер не мешает проектировать подтверждённый frontend/backend; зависимые конфигурации остаются отложенными. Если неизвестно, нужен ли собственный backend, агент показывает варианты и получает материальное решение по выбранному режиму взаимодействия, а не подставляет Supabase.

После этого агент показывает дерево с назначением каждой части и создаёт разрешённые файлы. До реализации функций доступны структура, навигация, план тестов и конфигурация согласованных инструментов. Отсутствие установленных инструментов или готовых функций отражается явно: «файлы подготовлены» не означает «приложение работает».

### Пример: отдельные frontend и backend с базой данных

Этот пример иллюстрирует выбранную архитектуру, не навязывает её всем проектам. Язык сервера, фреймворк, СУБД и провайдер здесь намеренно не заданы:

```text
project/
├── AGENTS.md                    # карта проекта и условная маршрутизация навыков
├── README.md                    # назначение, быстрый старт, ссылки
├── DESIGN.md                    # дизайн и его текущий статус
├── .gitignore
├── .env.example                 # только имена и безопасные примеры
├── apps/
│   ├── frontend/
│   │   ├── public/
│   │   ├── src/                # подразделение по выбранному UI-фреймворку
│   │   └── tests/
│   │       ├── unit/
│   │       └── components/
│   └── backend/
│       ├── src/                # API, бизнес-логика, работа с данными
│       ├── db/                 # если этот сервис владеет схемой БД
│       │   ├── migrations/
│       │   └── seeds/          # только безопасные тестовые/демо-данные
│       └── tests/
│           ├── unit/
│           └── integration/    # API, авторизация, сохранение, ошибки БД
├── tests/
│   ├── integration/            # только проверки между приложениями/сервисами
│   ├── e2e/                    # реальные действия браузера
│   └── fixtures/               # синтетические данные и безопасная подготовка
├── docs/
│   ├── README.md               # навигация; не копия содержимого всех документов
│   ├── architecture.md
│   ├── api.md                  # контракт собственного API
│   ├── local-development.md
│   ├── testing.md
│   ├── data-access.md          # модель данных, роли, доступ, границы доверия
│   ├── capabilities.md
│   ├── session-checkpoint.md
│   ├── context/
│   ├── specs/
│   ├── plans/
│   └── runs/<run-id>/          # progress и ссылки на доказательства
├── Feedback/
│   ├── README.md
│   └── preferences.md
└── .matreshka/runs/<run-id>/    # существующий ledger и его dashboard
```

Это целевой профиль, не утверждение о созданных сейчас файлах. Реальные манифесты, конфигурации и структура `src` соответствуют выбранному языку и фреймворку. Корневой `package.json` появляется только при необходимости JS-команд/workspaces; наличие backend не делает его Node.js-проектом. Конфигурация `playwright.config.ts` появляется при выборе Playwright. `.env.example` создаётся только для требуемой конфигурации, с указанием размещения переменных по приложениям и без значений секретов. Серверные секреты не попадают в frontend-конфигурацию.

Unit/integration-тесты принадлежат своему приложению; корневые тесты покрывают связи между приложениями и сквозные сценарии. Компонентные тесты могут располагаться рядом с компонентами. Пустые каталоги сохраняются принятой конвенцией только при наличии назначенного сценария; одинаковые проверки не дублируются на каждом уровне.

### Как меняется дерево по спецификации

| Архитектура | Размещение кода | Данные и проверки |
| --- | --- | --- |
| Раздельные frontend + backend | `apps/frontend/`, `apps/backend/` | Миграции у владельца схемы; серверные unit/API/integration и браузерный E2E |
| Единый fullstack-фреймворк | Например, `apps/web/` с клиентскими и серверными модулями по конвенции фреймворка | Серверная часть и её тесты явно указаны в AGENTS; отдельный фиктивный backend не создаётся |
| Frontend + готовый backend-сервис | `apps/frontend/`; каталог интеграции только для выбранного сервиса | Тесты контрактов, доступа, данных и E2E; собственный сервер добавляется, если он нужен по требованиям |
| Backend/API без UI | `apps/backend/` либо существующее корневое приложение | Серверные и сквозные API-тесты; browser E2E и DESIGN.md не обязательны без UI |
| Статический сайт | `index.html`, `assets/` либо существующая простая структура | Браузерные проверки; без runtime, БД и backend ради полноты дерева |

Размещение базы — отдельная ось для каждого подходящего профиля: существующая БД, локальная БД, собственный сервер или выбранный облачный сервис. Это не отдельные frontend/backend-архитектуры. Supabase-каталоги и правила появляются только после выбора соответствующих возможностей Supabase; использование его только для PostgreSQL не означает использование Auth, Storage или отказ от собственного API.

У схемы данных один явный владелец и одно каноническое расположение миграций; не создавать параллельные `db/migrations` и provider-migrations для одной схемы. `infra/` формируется при подтверждённом управлении инфраструктурой из репозитория; Docker не добавляется автоматически. Общие `packages/` добавляются только при реальном совместном использовании кода.

Для существующего проекта профиль сопоставляется с текущими путями; автоматического переезда в `apps/` нет. Уже существующие документы повторно не создаются под другими именами. Новая backend-функция в монолитном приложении не требует выделения отдельного сервиса.

## Как формируются и выполняются тесты

1. В интервью фиксируются критические пользовательские действия и последствия ошибок. Из них получаются строки в `docs/testing.md`: требование → слой проверки → сценарий → команда → окружение → владелец → доказательство.
2. На bootstrap создаются конфигурации выбранных средств, фикстуры и первые осмысленные проверки применимых поверхностей: доступной страницы frontend и подтверждённого контракта/запуска backend. Для backend сразу планируются unit-тесты бизнес-правил и интеграционные проверки API, прав и данных; папка frontend-тестов их не заменяет. Если поведение ещё не реализовано, проверка получает ожидаемый RED/NOT_RUN, а не заглушку `expect(true)`. Health endpoint не добавляется в продукт только ради теста; он проверяется при наличии такого требования.
3. В каждой задаче исполнитель добавляет/уточняет проверку поведения, получает ожидаемый RED, реализует изменение и получает GREEN. Запускает целевую проверку и ближайшие регрессии, а не весь набор после каждого изменения строки.
4. На границе готовой функции независимая проверка подтверждает применимые интеграции и критический путь в браузере. Перед передачей результата выполняются необходимая общая регрессия и сборка.
5. После подтверждения поведения обновляется затронутая документация. Контроллер сохраняет фактический результат в ledger, а dashboard и checkpoint отражают его. G4 остаётся отдельной независимой приёмкой в чистом контексте.

| Слой | Что доказывает | Пример для сайта тестирования знаний — предложение, сверить с принятой спецификацией |
| --- | --- | --- |
| Backend unit | Серверные бизнес-правила и граничные значения | Расчёт результата и запрет недопустимого перехода состояния |
| Frontend unit | Клиентские правила без обращения к серверу | Форматирование результата и локальная валидация ввода |
| Component | Поведение интерфейса изолированно | Выбор ответа, состояние загрузки, сообщение об ошибке |
| Backend integration/API | Работа серверных маршрутов, авторизации и хранилища | Сохранение попытки, повторный запрос, ошибка БД, отклонение недопустимых данных |
| Access control | Ограничения на фактических границах доверия: API и/или база | Пользователь A не может прочитать или изменить попытку B; RLS проверяется дополнительно, если выбран |
| Cross-service integration | Согласованность контрактов отдельных приложений/сервисов | Frontend получает согласованный формат результата и ошибки от backend |
| Browser E2E | Полный пользовательский путь | Вход → выбор теста → ответы → завершение → результат → обновление страницы и сохранённый результат |
| Visual/accessibility | Видимое состояние и доступность | Клавиатура, фокус, мобильная ширина, открытый диалог/меню |
| G4 | Соответствие исходному запросу пользователя | Независимая работа с продуктом без плана, спецификации и отчётов реализации |

Browser E2E с подменённым API может доказывать взаимодействие UI, но не сохранение в реальной базе. Это явно маркируется. API-тест не становится браузерным из-за имени папки. Ноль выполненных тестов или все skipped не дают PASS.

Первый выбор — уже принятый в проекте runner. Если его нет, применяется существующий выбор Matreshka из `browser-e2e.md` (Playwright как предложение для нового web-проекта). Версии определяются по совместимостям проекта во время реализации, не копируются из Vue/Jest-примера.

Проверки данных используют выбранную СУБД в выделенном тестовом окружении. Для PostgreSQL проверяются применимые транзакции, ограничения и миграции, а не их SQLite-имитация. Серверная авторизация проверяется пользовательскими запросами к API. Если архитектура использует RLS или прямой доступ клиента к данным, дополнительно проверяются соответствующие ограничения базы. Привилегированный клиент может готовить разрешённые фикстуры, но не подменяет пользователя в проверке запрета. Способ подготовки окружения — существующий тестовый экземпляр, локальный сервис или выбранный облачный провайдер — определяется отдельно. Без подходящего окружения интеграционные проверки остаются BLOCKED/NOT_RUN; unit-моки не закрывают пробел.

В документации фиксируются команды, которые действительно объявлены в проекте, с рабочим каталогом, слоем и владельцем. Команды frontend, backend, миграций и общего E2E перечисляются раздельно; язык backend определяет его runner. Для JS-части возможны `npm.cmd run test:unit`, `npm.cmd run test:integration`, `npm.cmd run test:e2e`, `npm.cmd run build`, но это не универсальные команды любого backend. Их нельзя объявлять работающими до создания scripts и проверки prerequisites. В полном E2E фиксируются адреса приложения/API, безопасная идентичность тестовой базы, владелец процессов и разрешённая очистка. Общие секреты, личный профиль браузера и рабочие данные не используются.

## Как передаются задачи

Используется существующий контроллер, его task ID, интерфейсные контракты и отчёты. Отдельный `tasks/done` с конкурирующими статусами не вводится.

```text
Подтверждённое требование
  → контроллер: узкая карточка и границы
  → исполнитель: код + целевые RED/GREEN проверки
  → reviewer: независимое чтение результата
  → одна согласованная волна исправлений при необходимости
  → техническая проверка нужного слоя / браузерного пути
  → обновление затронутой документации
  → ledger → dashboard и checkpoint
  → применимые финальные gates, включая отдельный G4
```

В task brief остаются цель, requirement ID, baseline, основной участок, точные разрешённые пути, нужный фрагмент интерфейса/дизайна, критерии, команда проверки, prerequisites, запреты и путь отчёта. Добавляется конкретная связь «критерий → слой теста → ожидаемый эффект → доказательство», если текущие поля оставляют её неявной.

Пример: задача UI показа результата получает контракт чтения результата и правила экрана; не получает право менять серверную авторизацию или алгоритм оценки. Задача backend получает серверный контракт, бизнес-правила, границы доступа и свои тесты; задача миграции — владельца схемы и отдельное доказательство совместимости. Эти роли могут выполняться одним агентом последовательно в небольшом проекте, но не смешивают полномочия. Несоответствие контракта возвращается контроллеру. Отчёт содержит изменённые файлы, фактические команды/exit codes, состояние проекта, непройденные проверки и ссылки на безопасные артефакты. Слова исполнителя «готово» недостаточно.

Один пишущий агент на checkout. Роли не получают право запускать дочерних агентов или расширять scope. Технический verifier не исправляет тесты и код. Роль документации меняет только заранее перечисленные документы после проверки поведения. G4 не получает карточки задач или эти отчёты.

## Поэтапная интеграция в Matreshka

Сложность `T2`: шесть проверяемых результатов. Профиль balanced; для задач, меняющих правила доступа/изоляции, отдельное усиленное security review в существующем бюджете. Здесь продуктовая UI-разработка отсутствует: `DESIGN_NOT_APPLICABLE`. Топология изученных участков актуальна; запускаемое окружение проектов не проверено.

Все пути ниже относительно `plugins/matreshka-agent/`. «Новый» обозначает предлагаемый файл. Работа последовательная: shared-файлы и один checkout исключают параллельных писателей. Все роли используют один baseline и принятые интерфейсы.

## Финальные проверки и предел доказательства

Два разных уровня: (а) работает ли обновлённый навык и создаёт ли правильные файлы; (б) работает ли сгенерированный продукт. Первый уровень не заменяет второй.

Архитектурные сценарии: frontend + собственный backend + PostgreSQL без выбранного хостинга; тот же проект с существующей БД на своём сервере; тот же backend с выбранным управляемым PostgreSQL; frontend + готовый backend-сервис по явному решению; integrated fullstack с серверными модулями; backend-only; static без БД; ещё не выбранный backend; существующая нестандартная структура. Для смешанного стека добавить fixture с JS-frontend и backend другого языка: навык не должен приписать серверу npm-команды. Выбор Supabase только для базы не должен удалять согласованный собственный backend или автоматически добавлять Auth/Storage.

Дополнительные поведенческие сценарии: повторный запуск; read-only; отсутствие browser runtime; API-only suite; все тесты skipped; запрещённый test reset; изменение команды и docs drift; восстановление сессии с устаревшим dashboard. Они дополняют существующие evals, а не заменяют их.

Для хотя бы одного fullstack-fixture с разрешённым окружением нужна реальная проверка цепочки frontend → backend → выбранная тестовая БД → frontend: действие, видимый результат, сохранение после перезагрузки. В отдельной одноразовой копии внести контролируемую поломку UI (например, разорвать обработчик отправки), получить ожидаемый FAIL и восстановить fixture. Отдельно нарушить серверное правило или сохранение данных и доказать, что backend-проверка обнаруживает дефект. Для разграничения доступа необходим отрицательный запрос чужого пользователя на выбранной архитектурной границе; RLS проверяется при его использовании. Если окружение недоступно, эти пункты остаются непроверенными и общий результат частичный.

Проверки разработчика плагина из корня репозитория после реализации:

```powershell
# Существующие проверки структуры пакета и development-контрактов.
# $pythonExe — заранее проверенный имеющийся интерпретатор; не установка.
& $pythonExe plugins/matreshka-agent/scripts/validate_dev_05.py
& $pythonExe plugins/matreshka-agent/scripts/check_dev_05.py
# Новые команды: станут доступны только после T5.
& $pythonExe plugins/matreshka-agent/scripts/test_project_bootstrap.py
git diff --check
```

Сохранить требуемые существующим CI проверки; перед реализацией прочитать актуальные workflow и baseline, а не считать прошлый зелёный запуск проверкой новых изменений. Фокусные проверки выполняются на каждой задаче, общий пакет и поведенческие сценарии — один раз на интеграционной границе и повторно только по затронутым отказам.

Бюджет: максимум две роли/четыре агентских хода на balanced-задачу; максимум одна согласованная волна исправлений. Для T3 при изменении security-контракта — до трёх ролей/шести ходов. Повторный существенный отказ → STOP_AND_RESCOPE. Дополнительные задачи не вводятся ради числа ролей или папок. Неисполняемые проверки получают честный статус и конкретную недостающую предпосылку.

Остановить зависимую работу при конфликте исходных требований, необходимости перезаписать пользовательский файл, изменении замороженного IC, отсутствии разрешения на runtime/данные или выходе за task scope. Независимую документальную работу можно завершить. Ни интервью, ни завершение сессии, ни слово «тест» не разрешают автоматически install, push или deploy.

**Что доказано сейчас:** конкретные отличия исходников и возможность встроить изменения в имеющиеся точки Matreshka. **Что должно быть доказано реализацией:** воспроизводимое создание файлов, работоспособность объявленных команд, обнаружение реальных дефектов и корректная передача задач. Ускорение разработки и экономия токенов пока не измерены; обещать их как полученный результат нельзя.
