# Проверка архитектуры и интеграция bootstrap/testing

Дата: 2026-10-21. Базовый commit: `cb188743d100f9fd72d59349bac5e75fa1bc0e17`.

Результат: изменения исходников готовы к проверке CI и публикации в ветке. Статус функциональности пакета остаётся `IMPLEMENTED_PENDING_NATIVE_VALIDATION`; установленный кеш и версия манифестов не обновлялись. Этот отчёт не является G4 или подтверждением работоспособности сгенерированного приложения.

## Сверка с учебным примером

Изучены `big-vibe-video` commit `eac290bba04f0c9a373cb609fb43aa00d2331c95`: структура apps, package scripts, Jest/Supertest setup, документация testing, task-creator/task-solver, роли coder/docs-maintainer; также предоставленная расшифровка. Ссылки и выводы сохранены в [плане](../plans/2026-10-21-project-bootstrap-testing-integration-plan.md).

Перенесены применимые принципы: разделение приложений, документация запуска/тестов, изолированные фикстуры, критерии в задачах и обновление документации после проверки. Не перенесены привязки к Vue/Express/SQLite/Pi, запрет исполнителю запускать тесты и автоматические Git-действия. API-тесты примера не объявлялись браузерными E2E.

Baseline-оценка текущих инструкций подтвердила: правила тестирования, сохранения существующей архитектуры, передачи задач и G4 уже были. Пробел состоял в конкретном bootstrap: профили, серверные test paths, команды/cwd, источники команд и связь с подготовленными конфигурациями. Это оценка применения инструкций, не наблюдение неправильного запуска установленного плагина.

## Изменения

- Пять архитектурных профилей; frontend/backend/СУБД/размещение выбираются независимо по спецификации. Свой backend сохраняется при выборе облачного PostgreSQL. Integrated fullstack и existing-project сохраняют серверные модули и текущие пути.
- Новый контракт `project-layouts.md`, поэтапный `testing-bootstrap.md`, шаблоны architecture/local-development/testing и условных API/data-docs. Lifecycle и краткая инструкция AGENTS ссылаются на них.
- Карта `docs/bootstrap.json`: структурная проекция принятых решений/проверок, без второго трекера задач. Документационные роли поддерживают существующие эквиваленты путей.
- Карточка/отчёт/dispatch связывают критерий с приложением, слоем теста, cwd, источником команды, безопасной средой и доказательством. Используются имеющиеся implementer/reviewer/verifier/docs/controller роли.
- Read-only checker проверяет существование объявленных файлов/обязательных документов, владение проверками, команды npm по настоящим scripts, формы статусов/доказательств, недопустимые пути. Он не исполняет команды, не читает env и всегда отделяет STRUCTURE_VALID от runtime NOT_VERIFIED.
- 21 детерминированный regression-тест, восемь новых сценариев eval coverage и шаг CI; отдельный бюджет условно загружаемых bootstrap-инструкций. README на русском объясняет этапы и получение команд для выбранного проекта.

## Независимое ревью и RED/GREEN

Начальный тест нового checker завершился 19 ожидаемыми отказами: механизм отсутствовал. После реализации базовые cases прошли. Ревью обнаружило два P2: преобразование `reason:null` в непустую строку и возможность убрать testing/local-development вместе с их декларациями. Отдельные отрицательные тесты воспроизвели оба дефекта до исправления. Добавлены строгий непустой string reason и обязательные document roles с поддержкой существующих путей. Повторное независимое ревью: оба замечания закрыты, блокеров публикации исходников не найдено.

Отдельный агент применил обновлённые инструкции к ограниченному fixture вне репозитория: React + Python API + PostgreSQL, хостинг не выбран. Созданы восемь документов/карта и frontend/backend/test/migration каталоги. После обновления schema и повторного запуска checker: exit 0, STRUCTURE_VALID, runtime NOT_VERIFIED; шесть runtime-строк остаются NOT_RUN. Сохранены независимые решения без навязанного провайдера.

Дополнительно оценены четыре варианта: integrated existing fullstack, API PASS без браузера, Supabase только как PostgreSQL hosting при своём backend, backend-only. Выходы соответствуют новым инструкциям. Это ограниченная проверка применения и извлечения инструкций, а не пять полных native-сессий.

## Границы подтверждения

- Fixture имел архитектурную постановку без выбранного предметного поведения и runner; не создавались фиктивные endpoints, package scripts или тесты для получения зелёного результата.
- Не запускались сгенерированные frontend/backend, браузерный E2E, реальная БД или controlled UI/backend mutation. Их проверка остаётся необходимой при приёмке конкретного runnable-проекта; текущий результат их не заменяет.
- Полный нативный онбординг, меню/dashboard/Feedback/session round-trip и G4 в установленном хосте для этой ревизии не выполнены. Установленная версия не подменялась исходниками.
- Структурный checker не доказывает достоверность отчётов, правильность архитектуры или полноту всех Markdown-ссылок; он проверяет объявленный ограниченный контракт. Runtime PASS требует отдельной свежей верификации.
- Разработка пользовательского сайта, установка инструментов, provisioning, публикация сайта и merge в main не входят в этот push изменений навыка.
